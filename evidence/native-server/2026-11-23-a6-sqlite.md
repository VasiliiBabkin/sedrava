## Observed results

- SedravaSQL: formatting and 6 Rust integration tests PASS; 45 durable
  application response records in one database, exact replay and conflicting
  reuse rejection across a full restart.
- Sedrava: 78 native Rust tests PASS, zero failures; locked build PASS.
- Server A1–A5 existing HTTP/state/security suites PASS (including A4
  debug crash windows). No A1–A5 migration or format changes.
- A6: 46 committed writes through real HTTP, original first reply replayed
  after >32 writes and restart, collision on key + modified request 409.
  SQL `audit` and `receipts` counts match commits; the state JSON contains
  no embedded receipt ledger.
- Two simultaneously running A6 servers with stale state: second writer
  fails closed (HTTP 503 + exit), no lost first write.
- Invalid or incompatible CLI mode combinations rejected without touching DB.
- Four SedravaSQL debug-only forced exits during A6 writes (after value,
  after audit, before COMMIT, after COMMIT): all recovered atomically;
  exact replay after committed-but-unanswered request. No physical power loss.
- A6 DSL read-only `db_get`: initial and changed external SedravaSQL value
  seen on GET without restarting; rejected as write step / POST expression;
  accepted only with explicit `--sqlite-v2-state`.
- Child executable runs with `PATH=/nonexistent`, no Python on runtime PATH.

## Boundaries and NO-GO

No power-loss test, independent real-device filesystem durability evidence,
formal transactional `begin/read/update/commit/abort` API, arbitrary SQL or
SQL DSL writes, automatic receipt retention/archival/quota management,
multiwriter server coordination, malicious same-UID protection, cross-OS
shipping tests or production readiness. SQLite WAL/FULL is used but not
a proof that the entire application is power-failure safe.
