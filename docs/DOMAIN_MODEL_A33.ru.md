# A33 — декларативная модель предметной области

Нормативная основа: [Декларация «Описал — получил»](DECLARATION.ru.md).
A33 — кандидат высокоуровневого слоя, а не новая публичная версия. Старые проекты формата 1 сохраняют прежний контракт. SedravaSQL не изменялся.

## Архитектурный шлюз

**Задача:** справочники заказчиков, объектов и оборудования A31/A32 требуют повторения схемы в миграциях, SQL API, сервисах и UI. Для типовых операций list/create и выбора родительской записи пользователь должен описывать сущность и поля один раз.

**До:** ручное определение таблиц/FK/индексов, маршрутов list/create, параметров/guards, UI-сервисов, полей форм и remote-pick. **После:** application, access, entity, типизированные поля и метки в domain.sdr. Эквивалентный результат по объёму именно среза A33: 16 строк/561 байт декларации вместо 199 строк app.sdr + 45 api.sdr + 40 migrations.json = 284 строки/10253 байта генерируемых низкоуровневых исходников (без общего манифеста и генерируемых HTML/CSS/JS). Сокращение 17.75x по строкам; не сравнение с полным A31: там больше функций, включая фильтрацию по родителю, транзакционные заявки и историю. Три сущности, восемь полей, две связи, шесть маршрутов и сервисов, семь миграций, две кнопки выбора родительских записей генерируются из декларации.

## Использование

[Рабочий пример](../examples/service_directory/domain.sdr). Сборка компилятора этой ветки, Linux GNU x86-64 проверен на VDS. Опубликованный alpha.3 не понимает формат 2.

```sh
cargo build --manifest-path rust/Cargo.toml --locked --bin sedrava
export PATH="$PWD/rust/target/debug:$PATH"
cd examples/service_directory
sedrava test
sedrava build
sedrava package --output /absolute/new/package
sedrava project verify-package /absolute/new/package
```

В каталоге проекта format 2 только sedrava-project.json и domain.sdr — исходники. Скомпилированные app.sdr, api.sdr, migrations.json, UI и checksums.json входят в неизменяемый проверяемый пакет, доступный для инспекции. Ручное смешивание двух форматов запрещено; пакет пересобирается из domain.sdr и проверяется побайтно. Сборка/тест не подключаются к рабочей БД. Для миграций и запуска применяются обычные project-команды с явно созданными приватными данными и файлом авторизации. См. [инструкцию A31](../examples/service_desk/README.ru.md), используя новый отдельный каталог данных, не базу service-desk. Сервер loopback, роли read/write; запись только при --allow-write.

## Контракт A33

- application с обязательной меткой; access session read write — явное принятие существующей двухролевой модели, не автоматическое создание пользователей, токенов или прав. У всех read доступ к спискам, у write также создание.
- 1..6 сущностей, 1..6 полей на сущность; имена ASCII lowercase/digits, начальная буква, максимум 20; четыре пробела. id — автоматически добавленный текстовый PK, значение вводит оператор (key guard); имя id зарезервировано. Метки 1..80 символов, без управляющих знаков, кавычек и обратных слешей. Бюджет исходника 16 KiB, действуют также прежние бюджеты генерации и БД.
- text MIN MAX (0..256 символов, MIN>0 также nonblank), int MIN MAX (i32), bool, ref EARLIER_ENTITY. Ссылки обязательны, циклы/forward-ref запрещены. SQL использует таблицы d_ENTITY и столбцы f_FIELD, FK на id, индексы ссылок. Типы enforced NativeLog; диапазоны/длины/nonblank enforced на generated API, не общие CHECK constraints в БД. Изменение диапазона/метки без изменения DDL не проверяет и не переписывает уже существующие строки; такое изменение правил требует отдельного анализа.
- Каждая сущность получает список с cursor after (20 строк, порядок ID), создание с idempotency и typed guards, форму, раздел и кнопки выбора дочернего контекста. Получение списков/переход на следующую страницу/обновление после записи пока ручные. Списки не фильтруются по родителю; нет редактирования/удаления, автоматических ID, nullable полей, дат, пользовательских операций, самостоятельной авторизации по сущности.
- Миграции: в порядке деклараций table, затем index/FK для каждой ссылки. Добавление сущности в конец сохраняет историю. Изменение существующего DDL, порядок, удаление сущности или downgrade не поддерживаются; отклоняются при проверке истории, без автоматического исправления или потери данных. A33 не переносит данные старого A31/A32, использует новый project identity.
- Детерминированные генерация, проверки и упаковка; нет ИИ-угадывания. Автор должен объявлять бизнес-правила. Формат 2 не поддерживает ручные расширения в этом срезе; прежний формат 1 остаётся доступен. Не production.

## Приёмка

88 Rust-тестов, включая два новых теста (детерминизм/append-only и негативные декларации), 50 прямых HTTP и 12 реальных HTTP из generated jsdom. Проверены роль read, replay, дубликаты, ограничения, FK, XSS-safe текст, переходы к связанным формам, пагинация, отказ от смешивания источников, повреждение каждого низкоуровневого файла пакета, изменение типа, добавление четвёртой сущности «Осмотры» с int/bool (7→10 миграций), pending gate, restart, сохранение старых записей и отказ downgrade. База тестовая. Настоящий браузер и независимый CI нового кандидата пока не проверены. Доказательства в evidence/a33-domain-model-2026-11-28/.

**Architecture Gate:** функциональный GO для ограниченного декларативного среза A33 при прохождении полной регрессии. Не GO для полной замены сервисного журнала и публичного релиза. Дальше: декларативные бизнес-операции с транзакционными инвариантами, затем автоматически выводимые зависимости/синхронизация и пользовательские представления. Не заставлять прикладного автора дублировать SQL/API/UI.

Полная регрессия A16–A25 (319 прямых HTTP, прежние DOM-тесты), семь alpha-сценариев и сервисный журнал A32 (68 прямых + 27 DOM HTTP) — PASS. Шлюз A33 пройден в ограниченной области.
