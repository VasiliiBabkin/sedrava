# A34 — декларативный жизненный цикл записи

Нормативная основа: [«Описал — получил»](DECLARATION.ru.md). A34 — кандидат поверх A33, не публичный релиз. Прежние format 1 и format 2 без workflow сохраняются. SQL-движок не изменён.

## Архитектурный шлюз

В сервисном журнале A31/A32 создание заявки, закрытие, повторное открытие и запись работы описывают каждый SQL, набор параметров, проверки, сервисы и формы вручную. A34 вводит декларацию переходов, из которой выводится этот ограниченный жизненный цикл.

```sedrava
workflow ticket:
    initial open
    transition work "Записать работу" from open to open
    transition close "Закрыть" from open to closed
    transition reopen "Открыть повторно" from closed to open
```

[Рабочий пример](../examples/service_workflow/domain.sdr): 27 строк / 991 байт декларации, четыре сущности, четыре таблицы и одна таблица событий, три объявленных перехода, 12 API-маршрутов, 13 миграций. Компилятор генерирует 367 строк app.sdr, 99 api.sdr, 70 migrations.json, всего 536 строк / 20232 байта, без манифеста и HTML/CSS/JS. Это объём одного и того же среза, не сравнение со всем A31 (в A31 есть дополнительные время, стоимость, фильтры и отчёты). 536/27 ≈ 19.85 по строкам. Автор объявляет состояния и допустимые переходы, но не повторяет транзакционные и UI-связки. Самопереход означает событие с изменением версии записи, а не пустую операцию.

## Контракт

- Один workflow для существующей сущности, после всех entity. 1..4 перехода, имена lowercase ASCII/digits (1..20, начальная буква), имена created/history зарезервированы; исходные состояния должны быть достижимы из initial. Метки и прочие пределы A33 сохранены. Никакого произвольного SQL, выражений или пользовательского кода внутри workflow.
- Компилятор добавляет w_status, w_revision и h_ENTITY (id,subject,kind,beforestate,afterstate,note) с FK и индексом. Создание основной записи включает initial и исходное событие created с тем же ID одной транзакцией. Событие created имеет пустой комментарий и beforestate, остальные требуют 1..256 символов, nonblank. Нет самостоятельного API изменения истории.
- Переход принимает subject, expected, event, note. Оператор задаёт уникальный ID нового события, выбирает запись с её текущей ревизией. UPDATE проверяет одновременно исходное состояние, ID и ожидаемую ревизию; INSERT сохраняет событие в той же транзакции. Дубли ID события (в пределах всего workflow) и устаревшая версия отклоняются без частичных изменений. Повтор запроса с тем же ключом и телом возвращает сохранённую квитанцию; изменение тела с тем же ключом отклоняется. Реализация опирается на существующие гарантии NativeLog и API, не обещает восстановление при физическом отказе диска.
- Списки/история читаются с курсором по ID (не хронологический порядок). Сгенерированный UI показывает статус/версию, выбор переносит ID/версию, кнопки переходов и форма комментария генерируются. Обновление списка после записи, новые ID и пагинация ручные; видимость кнопок пока не зависит от статуса, сервер проверяет правило. Сессии read/write, --allow-write, локальный режим; не допускается публичный deployment. Нет дат, автора события, времени/стоимости, произвольных guard-выражений, ролей отдельных переходов, удаления, редактирования.
- Схема истории генерируется после остальных таблиц; workflow нельзя безопасно добавить к существующей A33 сущности без отдельного плана миграции. Изменение правил переходов/initial, не меняющее DDL, не является миграцией и не валидирует прежние записи автоматически. Для этой версии применяйте неизменную декларацию workflow к данной БД; изменение действующей модели требует отдельного контракта миграции, которого пока нет. Используйте новую отдельную БД service-workflow. Не переносит существующие A31/A33 данные.
- Детерминированная сборка и точная проверка пакета, как A33. Новая грамматика требует компилятор этой ветки; опубликованный alpha.3 не поддерживает её.

## Приёмка

Проверены реальные сгенерированные API/UI/схема, атомарное создание, самопереход/закрытие/повторное открытие, отказ при неверном состоянии, устаревшей версии и повторном ID, read-only, FK, replay, перезапуск, проверка NativeLog, неизменный пакет. 40 прямых HTTP и 9 запросов из jsdom в первичном прогоне. Тест двух одновременных записей относится к предыдущему A32, отдельный конкурентный тест A34 пока не проведён. Настоящий браузер и независимая CI нового кандидата не проверены. Не production.

Следующий шаг — A35: автоматически выводимые зависимости чтения и записи и обновление интерфейса с сохранением безопасного повтора мутаций. Затем расширение декларативных представлений и операций с прикладными полями (время/стоимость). Не возвращаться к ручному описанию API, UI и SQL на прикладном уровне.

Финальная приёмка: 89 Rust, A34 40+9 HTTP, A33 50+12, A32 68+27, A16–A25 319 direct HTTP и прежние DOM проверки, семь alpha gates — PASS. Функциональный GO для ограниченного среза A34.
