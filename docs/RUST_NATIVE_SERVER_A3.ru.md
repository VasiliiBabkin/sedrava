# Sedrava Server A3 — ограниченный транзакционный HTTP

**Экспериментальный loopback-only режим. Это не СУБД, SQL,
production-сервис или доказательство устойчивости при сбое питания.**

## Запуск и пример

Пример: [transactions_a3.sdr](../examples/native_server/transactions_a3.sdr).

```sedrava
server "Transactions A3"
state count: int = 0
state total: int = 0
route GET "/summary":
    respond 200 { count: state.count, total: state.total }
route POST "/record":
    request amount: int
    require request.amount > 0
    set count = state.count + 1
    set total = state.total + request.amount
    require state.total <= 100
    respond 201 { count: state.count, total: state.total, accepted: true }
```

Синтаксис обработчиков остался A2, новая семантика включается явным
`--transactional` вместе с `--state-dir`:

```sh
mkdir -m 700 /ABSOLUTE/TRUSTED/new-a3-state
sedrava-native server run examples/native_server/transactions_a3.sdr \
  --port 8081 --max-requests 64 --idle-ms 30000 \
  --state-dir /ABSOLUTE/TRUSTED/new-a3-state --transactional
```

Каталог должен быть **новым, существующим, доверенным**:
абсолютный канонический путь без symlink, владелец — пользователь
сервера, права 0700. Запуск `--transactional` без `--state-dir`
запрещён. Не используйте рабочие данные или прежнюю папку A2:
новый формат `sedrava.server.transaction.v1` намеренно не
совместим с `sedrava.server.state.v1`. Ни обновление, ни откат
между схемами автоматически не выполняются.

## Протокол

```sh
curl -i http://127.0.0.1:8081/summary
curl -i http://127.0.0.1:8081/record \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: example-request-000001' \
  -H 'X-Sedrava-If-Revision: 0' \
  --data '{"amount":3}'
```

GET возвращает состояние и глобальную ревизию в заголовке
`X-Sedrava-Revision: 0`. После успешного POST сервер возвращает
`201`, обновлённые поля, и `X-Sedrava-Revision: 1`.

Повторяющийся POST/PUT/PATCH/DELETE с **тем же**
`Idempotency-Key` и идентичными методом, путём, Content-Type,
телом **байт-в-байт** и условием ревизии не исполняется повторно.
Возвращается сохранённый status/body и исходная ревизия,
`X-Sedrava-Replayed: true`. Даже если после этой транзакции
прошли другие успешные операции, старая квитанция по-прежнему
доступна. Текущую ревизию узнавайте новым GET.

Ключ — 12–64 ASCII-символа из букв, цифр, `_`, `-`, `.`.
Одинаковый ключ с другими параметрами даёт 409
`IDEMPOTENCY_CONFLICT`. Повторный заголовок отклоняется.

Необязательный `X-Sedrava-If-Revision` — проверка и условная запись
по глобальной ревизии (CAS). Для **нового** ключа устаревший
номер даёт 412 `REVISION_CONFLICT`. Повтор сохранённого запроса
разрешается из квитанции **до CAS** и не меняет состояние.
Номер ревизии — не HTTP ETag.

| Условие | HTTP / код |
|---|---|
| Нет ключа в изменяющем запросе | 428 `IDEMPOTENCY_KEY_REQUIRED` |
| Некорректный ключ | 400 `INVALID_IDEMPOTENCY_KEY` |
| Старый ключ и другие параметры | 409 `IDEMPOTENCY_CONFLICT` |
| Не совпала ожидаемая ревизия | 412 `REVISION_CONFLICT` |
| `require` не прошёл или переполнение int32 | 422 |
| Отказ записи до замены файла | 503 `STATE_WRITE_FAILED` |
| Неопределённый commit после rename | 503 `STATE_COMMIT_UNCERTAIN`, процесс прекращается |
| Квитанции заполнены | 507 `TRANSACTION_LEDGER_FULL` |

Ошибочные запросы и отклонённые записи не занимают ключ.
Успешный запрос занимает ключ даже при неизменном значении
состояния, так как фиксируется подтверждённая транзакция.

## Снимок, атомарность и ограничение ёмкости

- Состояние и все квитанции хранятся **в одном** файле
  `sedrava-state-v1.json` с новой схемой A3, общей ревизией,
  сигнатурой типа состояния и обязательными полями каждой
  квитанции: ключ, SHA-256 fingerprint запроса, статус и ответ.
- Поля, ревизии 1..N, уникальность ключей, форматы, типы,
  количество квитанций и JSON без дублированных ключей
  строго проверяются перед запуском TCP-порта.
- Фиксированный **невытесняемый журнал на 32 успешных запроса**.
  Новые записи после заполнения отклоняются (507), старые повторы
  остаются доступными. Автоматического TTL/удаления старых ключей
  нет — иначе их повтор исполнился бы снова.
- Ограничение всего JSON-снимка — **256 КиБ**. Превышение
  отклоняется до публикации нового состояния.
- Новый снимок записывается во временный файл в той же закрытой
  папке, выполняется `fsync` файла, атомарный `rename` и
  `fsync` каталога. При ошибке **до rename** состояние памяти
  остаётся прежним. При ошибке **после rename** результат
  неопределён, процесс останавливается и не заявляет прежнюю
  ревизию как подтверждённую.
- Только **один писатель на каталог**, сохранённые ограничения
  A2 для приватных файлов, запрещённых symlink/hardlink и
  эксклюзивной lock-записи. Lock после `SIGKILL` может остаться.
  Оператор удаляет его вручную **только после проверки, что
  прежний процесс действительно завершён**.
- Откат по `require` проверяется для нескольких состояний в
  одном обработчике. Одновременные запросы, процессы, файлы и
  SQL-операции не входят в эту модель транзакции.

## Что нельзя обещать

Это не абсолютная гарантия exactly-once. Повтор после успешного
подтверждения и штатного перезапуска защищён сохранённой
квитанцией; повтор после потери питания/диска, ручного отката
JSON-файла, неправильного удаления lock или подмены файла
может иметь другой исход. SHA-256 fingerprint обнаруживает
изменение *параметров запроса*, **не аутентифицирует файл и не
подменяет электронную подпись**.

Нет WAL, резервного журнала, crash-recovery после потери
питания, SQL, SQLite, автоматической компактизации, прав
пользователей, TLS, публичного bind, высокой нагрузки и
репликации. Локальные недоверенные процессы с правом записи
в каталог под тем же UID не входят в модель безопасности.

## Проверка

```sh
cargo test --manifest-path rust/Cargo.toml --locked --all-targets
python3 scripts/verify_native_server.py
python3 scripts/verify_native_server_a2.py
python3 scripts/verify_native_server_a3.py
```

Внешний Python-тест проверяет настоящий локальный HTTP,
идемпотентный повтор, CAS, полное восстановление после штатного
рестарта, несовместимость схем A2/A3, лимит 32 операций,
повтор после сбоя записи, проверку lock и тестовое завершение
процесса с последующим ручным восстановлением. Нативный сервер
при запуске не требует Python, Rust или pip.


Отдельное продолжение: [экспериментальный Server A4](RUST_NATIVE_SERVER_A4.ru.md)
с неизменяемыми записями redo-журнала, проверкой цепочки и
тестами прерывания процесса. Форматы A3 и A4 автоматически не
конвертируются.
