# Sedrava Server A9 — два ключа и серверное состояние в одной транзакции

Дата: 24 ноября 2026. Экспериментальный локальный серверный режим.
Не является полноценным языком SQL, общим ORM, публичным API и стабильным выпуском Sedrava.

## Что реализовано

A9 подключён к библиотеке SedravaSQL (проверенная и зафиксированная
ревизия исходников 7aad14da2af6310a5cc1deccdeecdcf6183c33f2).
Он использует новый opt-in B6 API, который в одной транзакции SQLite
записывает 2–4 ManagedPut и все квитанции. Специально для A9
ограничен синтаксис: РОВНО две операции изменения пользовательских
ключей и одно изменение поля состояния Sedrava Server.

Исполняемый файл examples/native_server/sqlite_a9_batch.sdr:

    server "A9 Atomic Pair"
    state counter: int = 0
    route PUT "/pair":
        request left: text
        request right: text
        request left_rev: int
        request right_rev: int
        db_batch_put "public_notes/left" = request.left expect request.left_rev
        db_batch_put "public_notes/right" = request.right expect request.right_rev
        set counter = state.counter + 1
        respond 200 { left: request.left, right: request.right, counter: state.counter }
    route GET "/snapshot":
        respond 200 { counter: state.counter }

Синтаксис на языке Sedrava напрямую выполняется родным Rust
интерпретатором/компилятором Server DSL, без Python runtime.

Ограничения декларации: только PUT; два разных статических
namespace/key (1..128 ASCII символов на часть, без префикса
sedrava_native), четыре различных объявленных поля запроса —
две строки text и две ожидаемые ревизии int — и ровно
одна инструкция set состояния. Смешивать с db_put A8,
require, несколькими set или динамическими путями нельзя.
Ответ строится из request, literals и вычисленного state.

## HTTP-протокол

Доступ только 127.0.0.1; сервер запускается с
--transactional --sqlite-v2-state /ABSOLUTE/PRIVATE/FILE.sqlite.
Дополнительный opt-in B6 таблицы включается только если в
исходной Sedrava-программе есть db_batch_put.

Запрос PUT /pair принимает Content-Type: application/json,
Idempotency-Key и X-Sedrava-If-Revision (ревизия серверного
состояния A6). Поля left_rev и right_rev содержат ОТДЕЛЬНЫЕ
ожидаемые ревизии двух пользовательских записей. Первоначальные
значения всех трёх ревизий — 0.

Ответ при успехе:
- HTTP 200 и исходный JSON с результатом и обновлённым состоянием;
- X-Sedrava-Revision: новая ревизия SERVER STATE;
- X-Sedrava-Batch-KV-Revisions: например 1,1 — новые ревизии
  первого и второго ключа в порядке объявленных db_batch_put;
- X-Sedrava-Replayed: true при точном повторе сохранённого запроса.

Квитанция включает версию контракта, подпись исходника, имя
маршрута, исходный Idempotency-Key, SHA-256 тела/условий,
ревизии двух ключей, ревизию состояния и весь HTTP-ответ.

Ревизии каждой из трёх строк проверяются внутри ОДНОЙ BEGIN
IMMEDIATE/COMMIT. До подтверждения коммита ответ 200 не
публикуется. Audit/receipts для всех трёх строк и общая квитанция
сохраняются в том же SQL-коммите. При несоответствии одной CAS
откатывается всё. Точный повтор отрабатывает до повторной
оценки state.set, поэтому не увеличивает счётчик ещё раз.

Важный случай конкурентности: если второй процесс успел
изменить строку состояния, прежний экземпляр после конфликта
останавливается вместо продолжения с устаревшим state.
При воспроизведении сохранённого ответа с более новой, чем
локальная, ревизией состояния сервер также переходит к
остановке после ответа. Старые квитанции из прошлого допустимо
воспроизводить и на более новом серверном состоянии.

Ошибки: 428 без ключа/условия, 400 неправильный ключ, 409
повтор ключа с другим телом, 412 stale CAS ключа или заголовка
состояния, 422 неверные/отрицательные ревизии и схемы запроса,
503 после неопределённого коммита или внешнего изменения
серверного состояния. Долговременное обслуживание после 503
не допускается без перезапуска и повторной загрузки состояния.

## Проверено на VDS

- 12 некорректных Sedrava-программ отвергнуты до bind.
- Реальный HTTP PUT/GET на 127.0.0.1, чтение записей
  независимо через CLI SedravaSQL и сравнение SQLite
  managed_batch_receipts / audit / receipts / records.
- Идемпотентный повтор, изменённый payload, конфликт ревизий
  любой из трёх строк, обновление одного ключа внешним CLI.
- Перезапуск Sedrava, сохранность старого ответа и
  восстановление счётчика из SQLite.
- Два одновременно работающих сервера: несогласованный
  экземпляр получает 503 и прекращает работу, новый
  экземпляр возвращает сохранённый повтор.
- Четыре DEBUG-only точки завершения процесса B6:
  after_first_value, after_all_rows, before_commit и
  after_commit. До коммита отсутствуют ВСЕ три строки,
  аудит и квитанции; после коммита все три строки,
  аудит и квитанции присутствуют и повтор распознаётся.
- Старые проверки A6/A7/A8 и Rust-tests SedravaSQL остаются
  обязательными.

## Что ещё НЕ реализовано

Полноценный SQL/DDL, пользовательские таблицы/индексы, произвольный
список ключей, DELETE, общие внешние транзакции, произвольные
выражения из запроса, авторизация, шифрование, согласованный GET
снимок двух разных ключей, online checkpoint, оптимизация
долгосрочного хранения или публичный API.

Чтение отдельных GET маршрутов не даёт снимок всех ключей
одновременно. Обычные SQLite-приложения, которые не включают B6,
не получают новую таблицу и не изменяют схему. Опыты над
SQLite-free NativeLog не участвуют в этой реализации.

Это не доказательство стойкости к настоящему обесточиванию
сервера. Не публикуйте локальный сервер в интернет и не
используйте систему для ценных пользовательских данных.
