# A37 — сервисный журнал из декларации

Нормативная основа: [Декларация «Описал — получил»](DECLARATION.ru.md).
Кандидат A37 поверх A36; не публичный релиз. [Исходник приложения](../examples/service_complete/domain.sdr).

## Архитектурный шлюз

Задача: перенести основные сценарии A31/A32 (четыре справочника/заявки, жизненный цикл, журнал, время, стоимость, фильтры и итоги) на единую модель. Ранее разработчик описывал SQL, параметры/guards, UI, маршруты, миграции и связывал их вручную. Теперь поля событий, их пределы, неучаствующие значения и допустимые переходы определены один раз:

```sedrava
workflow ticket:
    initial open
    event day: date label "Дата события"
    event minutes: int 1 1440 otherwise 0 label "Минуты работы"
    event cost: int 0 100000 otherwise 0 label "Стоимость (рубли)"
    transition work "Записать работу" from open to open capture minutes cost
    transition close "Закрыть" from open to closed
    transition reopen "Открыть повторно" from closed to open

report totals "Итоги выбранной заявки" from ticket history sum minutes cost
```

35 строк domain.sdr (1562 байта) генерируют 531 app.sdr + 132 api.sdr + 70 migrations.json = 733 строки (28817 байт). 733/35 ≈ 20.94 по строкам, без общего манифеста и HTML/CSS/JS. Это точное сравнение одной и той же модели A37; ручной A32 имеет 761 строку, но не полностью идентичный набор полей/представлений, поэтому число 761/35 не является доказательством функциональной эквивалентности. Генерация создаёт пять таблиц, 13 миграций, 16 маршрутов и 16 сервисов. Отчёты и зависимости выводятся без дублирования. Результаты измерений и хэши — evidence/a37-service-domain-2026-11-28/lowering-metrics.json.

## Контракт событий и отчётов

- В одном workflow после initial, до transition, можно объявить до трёх уникальных event NAME: date или event NAME: int MIN MAX otherwise VALUE, с обязательной меткой. Дата всегда обязательна при создании записи и каждом переходе. Это операторская календарная дата, не серверное время, часовой пояс или аудит автора. Guard require FIELD date в SQL API/host проверяет ASCII YYYY-MM-DD, 0001–9999, реальный день месяца и високосность Gregorian. В NativeLog дата хранится TEXT; ограничения проверяются API, не являются отдельным SQL-типом даты.
- capture перечисляет уникальные числовые event-поля, введённые на данном переходе. Для созданной записи и остальных переходов числовые поля получают явно объявленное otherwise, даже если в форме остались значения прошлого действия. Значение otherwise может намеренно быть вне диапазона capture (например, 0 минут). Числовые границы и otherwise лежат в [-500000,500000]; диапазоны проверяются на входе. В рамках лимита 4096 строк/индексного сканирования сумма ограничена 2048000000 по модулю, что помещается в i32. Результаты вне объявленного контракта отвергаются типизированным UI; прямое редактирование БД не квалифицируется.
- Создание/переходы атомарны с записью события. Сохраняются правила A34: compare-and-set версии, допустимое исходное состояние, уникальный event ID, идемпотентность, запрет произвольной записи в историю. Payload с лишними или отсутствующими полями отклоняется. Устаревшая форма не может повторно начислить стоимость. API не заменяет надёжность физического диска и резервное восстановление.
- report NAME LABEL from ENTITY history sum FIELD ...: 1..3 уникальных числовых event-поля, только существующий workflow. COUNT(*) и SUM по всей истории выбранной записи, включая событие created, независимо от курсора списка. Пустая/несуществующая запись даёт пустой результат. Пределы сканирования сохраняются; при превышении SQL возвращает ошибку, не частичную сумму. Никаких отдельных сохраняемых итогов и клиентской арифметики. Зависимости обновления выведены компилятором A35.
- view ... filter status для workflow принимает текст состояния (length 1..20, nonblank). Неизвестное состояние даёт пустой результат; неоднозначное явное поле status отклоняется. Остальные фильтры A36 сохранены. В новом примере динамический статус, фильтр по оборудованию, группировка по статусам и отчёт итогов; группировка приоритетов доступна в A36, но не включена в A37 из-за действующего бюджета 16 сервисов. Статусы open/closed и ID вводятся явно; выбор связанных записей помогает не копировать ID.
- Дата и числовые поля событий — общие поля в разделе заявки (перед кнопкой создания); вводятся вручную. Числа читаются только для соответствующих capture. Новые ID, ручные курсоры, первоначальная загрузка и повторный выбор версии после перехода остаются. История упорядочена по ID, не по дате. Нет назначения исполнителя, серверного времени, автора события, редактирования/удаления справочников, межпользовательской синхронизации, промышленной авторизации или восстановления после физического отказа. Не считать это полной feature parity за пределами проверенного среза.
- Формат 2, новая приватная база service-complete. Добавление event изменяет DDL истории; не переносит данные старых приложений. Не пытайтесь применить этот план к существующей A34/A36 БД; миграция таких изменений не реализована. Прежние проекты без event сохраняются. SedravaSQL не менялся. Только loopback и тестовые данные, не production.

## Испытания

92 Rust-теста, 90 прямых HTTP, 21 HTTP из generated jsdom. Проверены Gregorian даты и високосный год, создание с нулевыми метриками, ошибочные/лишние параметры, FK, read-only, атомарные переходы, два одновременных запроса разных авторизованных пользователей (один успех и один конфликт), replay, двойная запись отвергнута, rollback без изменений журнала, закрытие/повторное открытие без начислений, 105 минут/4000 RUB, отдельная история 23 события на двух страницах с точным итогом 44 минуты/66 RUB, автоматическое обновление и потерянный ответ, сохранность после restart, NativeLog verify и неизменность пакета. Настоящий браузер, независимая CI, релизная сборка и публичный deployment не квалифицированы. A37 сохраняет прежние возможности, но готовность к production не заявляется.

Финальная регрессия: A16–A25 (319 прямых HTTP и прежние DOM-сценарии), A32 (68+27), A33 (50+12), A34 (40+11), A35 (40+15), A36 (86+19), семь alpha gates — PASS. A37 — функциональный GO в ограниченной области, без production/release GO.
