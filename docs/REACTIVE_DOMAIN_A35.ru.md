# A35 — автоматические зависимости и обновление данных

Нормативная основа: [«Описал — получил»](DECLARATION.ru.md). Кандидат поверх A34, не новый публичный выпуск. SQL-движок не изменён.

## Архитектурный шлюз

До A35 оператор после создания записи или перехода обязан вручную обновить затронутые списки. В новом декларативном слое компилятор знает эффекты операций: создание сущности записывает её таблицу, workflow также записывает её историю. Поэтому компилятор выводит точные зависимости в пределах существующей модели, не заставляя автора приложения перечислять их. domain.sdr A33/A34 и их миграции/API неизменны; дополнительных строк прикладной декларации — ноль. Генерируемый низкоуровневый WebApp получает refresh list_ENTITY для создания и refresh list_ENTITY wf_history для создания/переходов workflow. Это не универсальный анализ произвольного SQL и не подписки на СУБД.

## Контракт

- Низкоуровневое свойство refresh — 1..8 уникальных имён сервисов. Источник: authenticated idempotent mutation с точной схемой write receipt (kind/affected/sequence/replayed); назначение: существующий authenticated non-idempotent SQL rows сервис без auto/cache. Не разрешены циклы через запись, неизвестные цели, неаутентифицированные цели, неверные типы квитанции. Прикладной domain.sdr это свойство не объявляет.
- Начальное чтение остаётся ручным. При отправке записи зависимые данные и прежние in-flight ответы инвалидируются, кнопки выбора исчезают. После подтверждения корректной квитанции write (affected>0, sequence>0) ранее запрашивавшиеся зависимые чтения выполняются заново в видимых разделах с текущими параметрами. Скрытые отложены до открытия. Незатронутые сервисы не запрашиваются. При изменении параметров tracked-чтения старый ответ исключается по поколению и сигнатуре. Автообновление не изменяет ID, ожидаемую версию или черновик формы. После перехода для следующей операции выберите свежую запись. Нет автообновления всех страниц курсорного списка, автоматического первого чтения, опроса, websocket, межвкладочной или межпользовательской синхронизации.
- Не более одной активной opt-in записи в этой вкладке. Она не отменяется только из-за навигации; запросы чтения с refresh могут возобновляться после возвращения в раздел. Неизвестный результат/ошибка/отказ не запускает автоматический повтор или обновление. Старые результаты уже удалены при отправке. Ручной повтор использует исходный ключ идемпотентности и прежнее тело. После подтверждённого replay применяется такое же обновление; 401 очищает защищённые результаты, а для pending-повтора сохраняется намерение чтения с прежней проверкой пользователя. Logout очищает данные и намерения обновления. Смена параметров, отмена и запоздалые ответы не возвращают старые строки. Действуют прежние сетевые бюджеты, ошибка обновления не превращает успешную запись в неуспешную. Если обновление не удалось, оператор может запросить список вручную. Серверная проверка revision/FK и транзакционные гарантии не заменяются клиентским refresh.
- Ранее существовавшие низкоуровневые сервисы без refresh сохраняют прежнюю семантику; пустые поля refresh/tracked не сериализуются в их конфигурацию (сохраняется прежнее построение ключей локального кеша). Для произвольного handwritten WebApp свойство refresh является явным контрактом автора, не доказательством read-only семантики внешнего HTTP сервиса.
- Пример и schema format 2 остаются прежними. Генерируемые пакеты требуют повторной сборки новым компилятором; старый публичный alpha.3 не изменён.

## Испытания

90 Rust, включая проверки контракта refresh. A35: 40 прямых HTTP и 15 реальных запросов в jsdom. Проверены автоматическое обновление уже открытого списка после создания, точное обновление списка/истории после перехода, неизменность несвязанного справочника, потерянный ответ после commit, отказ от старого ответа чтения, повтор с тем же ключом, скрытый раздел и сохранение черновика, logout. Прежний A34 также сохраняет свои серверные инварианты. Визуальной проверки настоящего браузера и независимой CI финального кандидата не проводилось. Не production. Дальнейший шаг: A36 — декларативные представления, фильтры и отчёты; A37 — полная прикладная модель.

Финальная регрессия: A16–A25 (319 direct HTTP и прежние DOM-сценарии), A32 (68+27), A33 (50+12), A34 (40+11 на runtime A35), семь alpha gates — PASS. Функциональный GO в ограниченной области A35.
