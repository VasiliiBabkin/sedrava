# A23d — серверные сессии локального SQL API

Опциональный режим `--session-ttl SECONDS` (1..3600 включительно) для `sedrava database-api run`. Требуется прежний приватный файл `--auth-file` A18. Без session-ttl прежний Bearer-режим сохранён. Включённый режим не принимает постоянные ключи на бизнес-маршрутах. Сервер остаётся на loopback; не выставлять через reverse proxy.

| Маршрут | Метод | Авторизация и результат |
|---|---|---|
| /session-policy | GET | Доступен при UI или сессиях, только {sessions: boolean} |
| /session-login | POST | Authorization: Bearer <постоянный ключ>, JSON {}; результат token, principal, role, expires_in |
| /session-logout | POST | Authorization: Session <временный токен>, JSON {}; результат revoked=true |
| Бизнес API | POST | Authorization: Session <временный токен> в режиме сессий |

Постоянные ключи (32 случайных байта в hex) и роли read/write по-прежнему назначает оператор. Временные ключи генерирует getrandom 0.4.3 (уже имелся в lockfile транзитивно). Сервер хранит SHA-256 сессионного токена, ID пользователя и monotonic deadline только в памяти, до 128 сессий всего и 4 на пользователя. Истечение абсолютное, не продлевается запросами. Вход при исчерпании лимита даёт 429 SESSION_CAPACITY. Просроченные записи удаляются при входе и выходе; проверка срока выполняется при каждом защищённом запросе. Logout отзывает только предъявленную сессию. Перезапуск уничтожает все сессии. При ошибке генератора токен не выдаётся. Маршруты сессий зарезервированы при включённом режиме или UI.

Ключи SQL-идемпотентности всё ещё связываются с API, маршрутом и постоянным идентификатором пользователя, а не с номером сессии. Тот же пользователь может повторить подтверждённую запись в новой сессии; другой пользователь не получает чужую квитанцию. Действующие правила и права всё равно проверяются. Формат базы данных и версия SQL-движка (363ccbc) не изменены.

UI получает режим доступа через /session-policy, хранит временный токен только в памяти страницы, не использует cookie/storage. Выход вызывает серверный отзыв. При 401 во время неопределённой записи интерфейс сохраняет исходный path/body/key/owner и позволяет повторить после входа с тем же principal. Вход другим пользователем не даёт повторить такую запись. Явный выход или перезагрузка страницы уничтожают локальное состояние повтора. Старый режим UI сохраняет прямую Bearer-авторизацию.

## Воспроизведение

Следовать инструкции A22 (схема, отдельный каталог данных, приватный auth-файл), добавить к команде запуска `--session-ttl 900`. Тесты:

```bash
export SEDRAVA_NATIVE_BIN=/absolute/sedrava
export SEDRAVASQL_NATIVE_BIN=/absolute/sedravasql-native-preview
python3 -B scripts/verify_sales_sessions_a23d.py
# DOM: Node 20+, jsdom 27.2.0, NODE_PATH на node_modules
SEDRAVA_A22_DOM=1 python3 -B scripts/verify_sales_sessions_a23d.py
```

41 прямой HTTP-запрос: неверные ключи/режим/параметры, разграничение ролей, лимит пользователя, отзыв, истечение, restart, одинаковый request key в разных сессиях. Проверяется неизменность БД при отказах. DOM через jsdom с реальным сервером: временный токен, потеря ответа после commit, отзыв сессии, повторный вход, изоляция principal, replay, logout, отсутствие browser storage. Повторно PASS A23c 33, A23b 129, A23a 30, A17–A21 63 и A22 HTTP/DOM. Данные временные; production-службы и файлы не затронуты. Логи в evidence/a23-sessions-2026-11-27.

## Границы

Нет регистрации пользователей, паролей, password hashing, изменения ролей/ключей без перезапуска, списка/массового отзыва сессий, rate limiting, TLS, cookie-based login, постоянных сессий, публичного production-развёртывания. Глобальный лимит 128 задан кодом, отдельно не тестировался на заполнении 128 сессий. Пользовательский каталог пока приватный JSON-файл, не таблица БД. Пользовательский интерфейс написан HTML/CSS/JS, не генерируется Sedrava. Проверка реальным браузером и независимая Forgejo CI не выполнены. Строгий Clippy всего проекта ранее не проходил. Не использовать ценные данные.
