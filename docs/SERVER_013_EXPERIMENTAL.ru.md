# Sedrava: сервер и SQLite — экспериментальный срез 0.13 A1

**Статус: отдельный PR, не выпущен.** Не входит в 0.11.0 или экспериментальную 0.12. Подготовлен на стабильной 0.11; интеграция с пространствами имён 0.12 потребуется отдельно.

## Реализуемая функциональность

Новый тип декларативного исходника — server. В файле examples/server_013_tasks.sdr описываются SQLite через имя переменной окружения, версии миграций, создание таблиц, добавление колонок с обязательным значением по умолчанию. Разрешены только типы int (int32), bool и text(N) длиной от 1 до 1024. Произвольный SQL, удаление/переименование столбцов, запуск Python-кода из источника запрещены. Пределы: 128 миграций и 32 поля в таблице.

Пример из экспериментальной ветки:

~~~sh
python sedrava_cli.py check examples/server_013_tasks.sdr
python sedrava_cli.py build server examples/server_013_tasks.sdr --output build/taskboard-server
export SEDRAVA_DB_PATH="$PWD/build/taskboard.db"
python build/taskboard-server/server.py migrate
python build/taskboard-server/server.py check

# ASGI-сервер — отдельная зависимость:
python -m pip install uvicorn
cd build/taskboard-server
python -m uvicorn server:app --host 127.0.0.1 --port 8000
# Проверка: GET http://127.0.0.1:8000/health
~~~

Выходные файлы: server.py, исходник source.sdr, schema.json, README.md. Импорт ASGI-приложения только проверяет актуальную версию схемы; он **не запускает миграции автоматически**.

## Сохранность данных

- Каждая миграция и её SHA-256 записываются в таблицу _sedrava_migrations. Изменение применённой миграции, пропуск версии, попытка запуска старого сервера на более новой схеме приводят к отказу.
- Миграции выполняются в SQLite внутри одной транзакции BEGIN IMMEDIATE. При ошибке — ROLLBACK, в том числе для DDL-операций.
- Поля добавляются только с NOT NULL и проверенным литералом default, чтобы существующие записи оставались допустимыми.
- Перед обновлением остановить сервер и создать проверенную резервную копию: python server.py backup /absolute/path/new-backup.sqlite. Используется SQLite backup API; существующий файл назначения нельзя перезаписать.
- Автоматических DOWN-миграций нет. Возврат к старому серверу требует офлайнового восстановления резервной копии с остановленными процессами (включая корректную работу с файлами WAL/SHM).
- Схема в schema.json проверяется повторным разбором source.sdr.

## Чего **нет**

Пока работает только ASGI GET /health (остальные пути 404). Нет CRUD, аутентификации/авторизации, изоляции пользователей, PostgreSQL, миграций клиентских Web/Android хранилищ, безопасного сетевого деплоя и гарантий многопользовательской работы. **NO-GO для публичного API с реальными пользовательскими данными.**

Следующий этап: типизированные декларации серверных маршрутов, транзакционные операции с данными, авторизация на уровне записей, проверка конкуренции и восстановление из бэкапа, затем адаптер PostgreSQL.

Источники: https://www.sqlite.org/lang_altertable.html и https://docs.python.org/3/library/sqlite3.html
