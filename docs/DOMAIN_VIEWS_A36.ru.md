# A36 — декларативные представления и отчёты

Нормативная основа: [«Описал — получил»](DECLARATION.ru.md). Кандидат поверх A35, не публичный релиз. SedravaSQL не изменён.

## Архитектурный шлюз

Сервисный журнал требует отдельных выборок открытых заявок, заявок оборудования и сводных показателей. Ранее прикладной автор должен был вручную дублировать схему в SQL, параметрах API, типах ответов, состояниях/формах и зависимостях refresh. Теперь он описывает только желаемые представления:

```sedrava
view open "Открытые заявки" from ticket where status = open
view equipment "Заявки оборудования" from ticket filter asset
report statuses "Заявки по статусу" from ticket group status count
report priorities "Заявки по приоритету" from ticket group priority count
```

[Рабочий пример](../examples/service_views/domain.sdr). Четыре декларации добавляют четыре SQL query, маршрута и типизированных сервиса, четыре панели, проверяемые входные параметры и выводимые зависимости A35. Фильтр по ref получает кнопку выбора в родительском справочнике; выбор заполняет ID фильтра, сбрасывает его курсор и открывает нужный раздел. Новых миграций не требуется. Результат сравнивается с тем же функциональным срезом, не со всем A31.

## Контракт A36

- Не более четырёх view/report вместе, после entity и необязательного workflow. Уникальные имена ASCII по правилам A33. Указывается существующая сущность, метка и одно из трёх выражений: where status = STATE, filter FIELD, group FIELD count. В произвольный SQL, имена внешних таблиц или expressions это не преобразуется; неизвестные поля и состояния отклоняются. where status и group status относятся к сгенерированному статусу workflow; неоднозначность с явно объявленным полем status отклоняется. Обычное поле status в сущности без workflow остаётся обычным полем.
- Представление возвращает все поля сущности и статус/версию, если имеется workflow. where status = STATE — фиксированная выборка допустимого состояния. filter FIELD — точное равенство по text/int/bool/ref, параметры и guards выводятся из исходного типа. Значение фильтра передаётся как параметр SQL, не подстановка текста. Ref позволяет выбрать ID родителя; фильтрация по имени/подстроке и произвольные комбинации предикатов не реализованы. Списки: по 20 строк, порядок по ID, ручной курсор. Выбор строки с workflow переносит актуальную ревизию для защищённого перехода.
- report group FIELD count: workflow status, bool либо целое поле с диапазоном не более 20 значений. СУБД группирует все подходящие записи, не текущую страницу; COUNT(*) возвращает количество, группы упорядочены по ключу, отсутствующие группы не заполняются нулями. Пустой набор даёт пустую таблицу. API требует фиксированный пустой cursor after, выборка id>'' включает все допустимые непустые ID. LIMIT 21 — sentinel для UI (max-items 20): при выходе за контракт группировки интерфейс отвергает результат, не показывает усечённый отчёт. Прямой низкоуровневый API возвращает до 21 группы; при нарушении модели вызывающий обязан считать 21 результат ошибкой полноты. Предполагается запись через объявленные guards, а не произвольная правка хранилища. Действуют существующие лимиты NativeLog/SQL (сканирование до 4096 строк, при превышении — ошибка, не обещание неограниченных отчётов). SUM/AVG, составные группы, JOIN и произвольные агрегаты пока не поддерживаются высокоуровневым синтаксисом.
- Все чтения session-authenticated, без idempotency и persistent cache. Изменение сущности затрагивает также её представления/отчёты. После подтверждения записи обновляются ранее запрошенные зависимые панели; при смене параметров старый ответ инвалидируется, скрытый раздел отложен, остальные сущности не обновляются. Нет автоматического первого запроса, межпользовательской синхронизации и автоматического повторения мутаций. Сохранены существующие ограничения 16 сервисов/24 API, бюджеты дерева UI/запросов и ограничения A33/A34. Четыре представления не гарантированы при любой комбинации сущностей и переходов; избыточная модель диагностируется при сборке.
- Формат 2, неизменная schema, новый отдельный проект service-views. Для запуска нужен компилятор A36 этой ветки, не прежний публичный alpha.3. Никакой миграции данных старых A31/A34 примеров. Режим loopback, тестовые данные, не production.

## Проверки

Проверки проводятся на VDS с NativeLog 0.0.2 и сгенерированным UI (jsdom, не визуальная проверка настоящего браузера). Сценарий включает 23 записи при размере страницы 20, две страницы, групповые количества 11/11/1, фильтр по оборудованию, защиту типов и сессии, read-only журнал, выбор записи, изменение статуса, целевые обновления и очистку после logout. Доказательства и финальные числа — в evidence/a36-domain-views-2026-11-28. Независимый CI и другие платформы не квалифицируются этим прогоном.

Финальная приёмка: 91 Rust, 86 direct HTTP + 19 реальных запросов generated DOM. A16–A25 (319 direct HTTP и предыдущие DOM-сценарии), A32 (68+27), A33 (50+12), A34 (40+11), A35 (40+15), семь alpha gates — PASS. 4 декларации (5 строк с пустым разделителем) добавляют 141 строку app.sdr/api.sdr; 27→32 строки исходника, 543→684 строки генерируемых app/api/migrations. Миграции побайтно идентичны. Проверены пустые отчёты, результат при закрытии и точные количества после перезапуска. Функциональный GO в ограниченной области A36, без утверждения production readiness.
