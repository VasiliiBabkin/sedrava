# Sedrava Server A4 — ограниченный журнал транзакций и восстановление

**Статус: экспериментальный прототип. НЕ предназначен для production,
публичного доступа, банковских расчётов и пользовательских данных.**
Поддерживаются только Unix-платформы и локальный адрес `127.0.0.1`.
Это **не** SedravaSQL и **не** завершённый WAL/SQL-движок.

A4 продолжает [Server A3](RUST_NATIVE_SERVER_A3.ru.md): типизированные
состояния `int/text/bool`, `set`/`require`, глобальная ревизия,
`Idempotency-Key` и повтор уже подтверждённого ответа сохраняются.
Новый режим хранения включается только явно; A2/A3 не меняются.

## Первый запуск

Пример: [redo_journal_a4.sdr](../examples/native_server/redo_journal_a4.sdr).

```sedrava
server "Redo Journal A4"
state count: int = 0
state total: int = 0
route GET "/summary":
    respond 200 { count: state.count, total: state.total }
route POST "/record":
    request amount: int
    require request.amount > 0
    set count = state.count + 1
    set total = state.total + request.amount
    require state.total <= 100
    respond 201 { count: state.count, total: state.total, accepted: true }
```

Приведённые операции используют уже существующий DSL A2/A3.
Для включения A4 создайте **новую, пустую, доверенную** папку с
каноническим абсолютным путём, владельцем процесса и правами 0700:

```sh
mkdir -m 700 /ABSOLUTE/TRUSTED/new-a4-journal
sedrava-native server check examples/native_server/redo_journal_a4.sdr
sedrava-native server run examples/native_server/redo_journal_a4.sdr \
  --port 8081 --max-requests 64 --idle-ms 30000 \
  --state-dir /ABSOLUTE/TRUSTED/new-a4-journal \
  --transactional --journaled
```

Без `--transactional` использование `--journaled` отклоняется. Без
`--state-dir` транзакционный режим не запускается. Сервер слушает
**только 127.0.0.1**, не создаёт systemd-службу, TLS, пользователей,
доступа к произвольным файлам или внешнего HTTP.

Пример записи и чтения:

```sh
curl -i http://127.0.0.1:8081/summary
curl -i http://127.0.0.1:8081/record \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: a4-example-request-0001' \
  -H 'X-Sedrava-If-Revision: 0' \
  -d '{"amount":3}'
```

Повторите **ту же команду** с теми же байтами тела, ключом и
ожидаемой ревизией — сервер возвращает сохранённый ответ и
`X-Sedrava-Replayed: true` без второго изменения счётчика.
Получить **текущую** глобальную ревизию можно отдельным GET.

## Что записывается на диск

В отличие от A3, который атомарно заменяет **один JSON-снимок**,
A4 сохраняет **отдельный неизменяемый файл на успешную транзакцию**:

- `sedrava-journal-v1.manifest.json` — постоянный маркер формата,
  подпись исходника/объявлений состояния и лимит журнала.
- `sedrava-state-v1.json` — **защитная заглушка, а НЕ снимок A2/A3**.
  Внутри намеренно несовместимый JSON. Даже прежние бинарники A2/A3,
  не знающие о маркере A4, должны отклонить такую папку до
  открытия HTTP-порта.
- `txn-00000001.json`, `txn-00000002.json` и далее до
  `txn-00000032.json` — последовательные подтверждённые записи.
- `.sedrava-server.lock` — эксклюзивная блокировка процесса;
  удаляется только при штатном завершении.

Каждая запись содержит схему `sedrava.server.redo-journal.v1`,
номер ревизии, полное типизированное состояние **после** действия,
квитанцию запроса (ключ, fingerprint, HTTP-статус, JSON-ответ),
хеш предыдущей записи и собственный SHA-256 хеш. Это
**ограниченный append-only redo journal**, не полноценный WAL.
Отдельный checkpoint пока не реализован.

Порядок подтверждения новой операции:

1. Проверяется типизированный кандидат состояния, квитанция,
   лимиты журнала и наличие свободного номера ревизии.
2. Создаётся новый временный приватный файл в том же каталоге.
3. Запись JSON, `fsync` файла, атомарный `rename` в уникальное имя.
4. `fsync` каталога; **только после успешного возврата**
   формируется HTTP-ответ об успешной транзакции.
5. При ошибке **до rename** сохранённые состояние и квитанция
   не заменяются. При ошибке **после rename** исход может быть
   неопределён: сервер выдаёт 503, не заявляет ложную прежнюю
   ревизию и прекращает работу.

При новом запуске журнал читается **с первой ревизии**.
Обязательны непрерывная последовательность, исходная
сигнатура, верные типы, связанные SHA-256 хеши, уникальные
квитанции, разрешённый формат всех файлов. Пропуск ревизии,
повреждение JSON, дубли полей, symlink/hardlink, лишний файл,
сторонний снимок A2/A3 и несовместимое содержимое приводят к
**отказу запуска до открытия TCP-порта**.

Особенность A4: журнал привязан к **SHA-256 исходного .sdr-файла
байт-в-байт**. Даже изменение комментария блокирует восстановление
без отдельно разработанной и проверенной процедуры миграции.
Это строгий защитный контракт экспериментальной версии.

## Строгие ограничения и восстановление после аварии

- **Один пишущий процесс на каталог**. Нет многопроцессных
  транзакций, конкурентных соединений, очередей, репликации или
  автоматической эвакуации lock-файла.
- **32 подтверждённые операции без вытеснения** и максимум
  **256 КиБ на запись**. Достигнут предел — новые записи отвергаются
  с HTTP 507, сохранённые квитанции по-прежнему доступны для повтора.
- После `SIGKILL` может остаться `.sedrava-server.lock`.
  **Не удаляйте** его, пока не проверили, что прежний процесс
  завершён. В тестах восстановление выполняется только в
  собственных временных каталогах после завершения дочернего процесса.
- Если процесс завершился **до rename**, возможен лишний
  временный файл. A4 **не удаляет и не игнорирует его автоматически**:
  откажется запускаться, пока оператор не изучит причину.
- Если процесс завершился **после rename**, файл подтверждения
  может уже быть виден. A4 восстанавливает доступную корректную
  цепочку, но **не доказывает**, что данные гарантированно пережили
  бы отключение питания в тот же момент.
- Хеши служат для обнаружения случайных повреждений и изменений
  цепочки, **не являются HMAC, подписью или защитой от подделки**
  файлов процессом с доступом к директории. Восстановление
  не защищено от отката всей папки к предыдущей валидной версии.

Защитная заглушка проверяется на точное содержимое, отсутствие
символических и жёстких ссылок и режим доступа. При первом запуске
заглушка создаётся и синхронизируется **до** манифеста. Если процесс
аварийно завершится посередине начальной инициализации, повторный
запуск может отказать и потребовать ручной диагностики.

**Предыдущие экспериментальные A4-каталоги без защитной заглушки
не открываются новым бинарником автоматически.** Создайте новый
пустой каталог или используйте отдельно проверенную процедуру
миграции. Это сознательная несовместимость ради защиты старых данных.
- Нельзя обещать абсолютное **exactly-once** при сбоях питания,
  потере диска, откате журнала, ручных изменениях и
  конкурентном злонамеренном доступе того же Unix UID.

A4 не делает автоматическую миграцию A2/A3. Использование одного
каталога разными форматами отклоняется. Для перехода потребуются
отдельный инструмент экспорта, проверка контрольных сумм,
резервная копия и явное подтверждение оператора.

## Независимые испытания на VDS

```sh
cargo fmt --manifest-path rust/Cargo.toml --all -- --check
cargo test --manifest-path rust/Cargo.toml --locked --all-targets
python3 scripts/verify_native_server.py
python3 scripts/verify_native_server_a2.py
python3 scripts/verify_native_server_a3.py
python3 scripts/verify_native_server_a4.py
```

A4-тесты проверяют настоящие HTTP-запросы через `127.0.0.1`,
повтор ключей после рестарта, 32 записи, отказ при повреждении
цепочки и маркера, защиту от совместного открытия с A2/A3,
принудительный `SIGKILL` и четыре точки аварийного завершения:
после записи, после `fsync` временного файла, после `rename`,
после `fsync` каталога.

**Только отладочная сборка** реагирует на переменную
`SEDRAVA_A4_FAULT`. Release-бинарник не должен использовать
эту переменную и не содержит её эффекта аварийного выхода.
Проверки не являются тестированием физического power-loss,
разных файловых систем или полноценного WAL. Рабочие сайты,
серверные порты, nginx и данные пользователей не затрагиваются.
