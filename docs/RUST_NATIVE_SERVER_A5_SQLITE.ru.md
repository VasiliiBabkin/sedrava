# Sedrava Server A5 — хранилище на SedravaSQL / SQLite

Статус: **экспериментальная интеграция**. Прототип работает на
Ubuntu Linux x86_64, не предназначен для хранения важных данных.
Нет публичного слушателя, TLS, SQL-запросов из Sedrava DSL,
многопроцессной координации HTTP-состояния или production-гарантий.

Основной шаг: вместо переписывания самодельного JSON-журнала
сервера A4 используется отдельная библиотека
[SedravaSQL](https://github.com/VasiliiBabkin/sedravasql), зафиксированная
по SHA **b5831d7c5961042ff37feaaf4b4fef59b81b5f64**.
Она сама работает через SQLite WAL, `synchronous=FULL`, транзакции
`BEGIN IMMEDIATE` и параметризованные SQL-запросы.

## Запуск

Пример: [sqlite_a5.sdr](../examples/native_server/sqlite_a5.sdr).
Операции `state`, `set`, `require` и HTTP-синтаксис остаются
из [Server A3](RUST_NATIVE_SERVER_A3.ru.md).

Создайте **новый отдельный приватный каталог** и используйте
другой файл, не прежние JSON-каталоги A2/A3/A4.

```sh
mkdir -m 700 -p /ABSOLUTE/TRUSTED/sqlite-a5
sedrava-native server check examples/native_server/sqlite_a5.sdr
sedrava-native server run examples/native_server/sqlite_a5.sdr \
  --port 8081 --max-requests 64 --idle-ms 30000 \
  --sqlite-state /ABSOLUTE/TRUSTED/sqlite-a5/state.sqlite \
  --transactional
```

Параметр `--sqlite-state` требует `--transactional`.
Он **несовместим** с `--state-dir` и `--journaled`; сервер отклоняет
сочетание до открытия TCP-порта. A1–A4 остаются без изменений.
SQLite-файл на Unix создаётся с правами **0600**, чужие/общедоступные
файлы, symlink и hardlink отклоняются самой SedravaSQL.
Родительский каталог должен быть доверенным и приватным (0700).
Злонамеренные операции другого процесса с тем же UID
**не** входят в модель безопасности.

```sh
curl -i http://127.0.0.1:8081/summary
curl -i http://127.0.0.1:8081/record \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: sqlite-example-0001' \
  -H 'X-Sedrava-If-Revision: 0' \
  -d '{"amount":3}'
```

## Данные, ревизии, транзакции

В SedravaSQL создаётся SQLite-схема 1 с таблицами `records`,
`audit` и `receipts`. Сервер хранит типизированное состояние
и квитанции A3 в одном JSON-значении ключа, выделенного исходнику.
Каждая запись обновляет ключ с CAS по ревизии **в одной
SQLite-транзакции**, вместе с записью в `audit` и `receipts`.

Ключ данных привязан к SHA-256 **полного исходного кода**.
При изменении программы получится иной ключ, а не автоматическая
миграция. В том же SQLite-файле могут находиться разные исходники,
но **одновременно писать в одно серверное состояние нескольким
процессам не поддерживается**.

- После штатного перезапуска A5 восстанавливает состояние
  и подтверждённые ответы; идентичный HTTP-запрос по прежнему
  ключу вернёт старый ответ, не выполняя действие второй раз.
- Необязательный `X-Sedrava-If-Revision` защищает от устаревшего
  изменения. Повтор сохранённого запроса проверяется до CAS.
- При одновременной работе двух серверных процессов с одной
  базой SQLite отклоняет запись устаревшего значения. Сервер
  получает **503** и останавливается, не продолжая работу
  с устаревшим состоянием. Это защитный отказ,
  **не** автоматическая синхронизация.
- Ограничение **32 квитанции** из A3 в серверном состоянии
  пока **сохраняется**. Сама SQLite поддерживает более масштабное
  хранение, но это ещё не полноценная миграция серверного API.
- Если SQLite сообщает ошибку commit, сервер считает
  результат **потенциально неопределённым**, отвечает 503
  и прекращает обработку. После проверки файла и восстановленного
  состояния оператор может перезапустить экспериментальную службу.

## Бэкап и восстановление

Работать с той же SQLite-базой можно через независимую CLI SedravaSQL:

```sh
sedravasql verify /ABSOLUTE/TRUSTED/sqlite-a5/state.sqlite
sedravasql backup /ABSOLUTE/TRUSTED/sqlite-a5/state.sqlite \
  /ABSOLUTE/TRUSTED/sqlite-a5/backup.sqlite
sedravasql verify /ABSOLUTE/TRUSTED/sqlite-a5/backup.sqlite
```

SQLite Backup API проверен на VDS с незавершённым checkpoint
в отдельном WAL-файле. Прямое копирование одного работающего
`.sqlite`-файла вместо Backup API **не рекомендуется**.
Здесь нет автоматического расписания, репликации или резервирования.

## Проверено

```sh
cargo test --manifest-path rust/Cargo.toml --locked --all-targets
python3 scripts/verify_native_server.py
python3 scripts/verify_native_server_a2.py
python3 scripts/verify_native_server_a3.py
python3 scripts/verify_native_server_a4.py
python3 scripts/verify_native_server_sqlite.py
```

Отдельный Python-клиент делает реальные HTTP-запросы через
`127.0.0.1`, проверяет квитанции и восстановление после нового
процесса, инспектирует настоящую SQLite-схему и аудит, делает
backup через независимый SedravaSQL, испытывает **два
одновременно живых сервера** и отказ второго процесса при
устаревшем CAS. Сервер работает при `PATH=/nonexistent`.

Всё это **не** подтверждает сохранность при физическом
отключении питания, корректность произвольных SQL-программ,
кроссплатформенную релизную матрицу или готовность СУБД для
чужих приложений. Прототип SedravaSQL и путь дальнейшего
развития описаны в её отдельном репозитории.

Следующий отдельный экспериментальный режим —
[Server A6](RUST_NATIVE_SERVER_A6_SQLITE.ru.md): новые
`--sqlite-v2-state` и `db_get`, без ограничения 32 ответов.
A5 продолжает работать со своей схемой; автообновления хранилища нет.
