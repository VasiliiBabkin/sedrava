# A23a — декларативные ограничения входных параметров

В `database` и внутри маршрута `database-api` после всех `param` и до единственного `query`, `execute`, `transaction` или `sequential` можно объявить до 64 правил. Правила проверяются совместно (AND). Неизвестные параметры, несовместимый тип, повтор одного правила, перевёрнутые пределы, нарушение порядка и неизвестный синтаксис отклоняются при check.

```text
    param id: text
    param amount: int
    require id key
    require amount range 0 2147483647
```

- `require NAME range MIN MAX` — включительные границы i32.
- `require NAME length MIN MAX` — включительные границы количества Unicode scalar values, 0..65536 (не байты и не графемы).
- `require NAME nonblank` — непустая после Rust trim строка; исходное значение не изменяется.
- `require NAME key` — 1..128 ASCII символов [A-Za-z0-9_.-].

Сначала типизация, затем ограничения, затем SQL. В HTTP после проверки полномочий и структуры тела ошибка правила — 422 REQUEST_REQUIREMENT_FAILED (отличается от REQUEST_SCHEMA_MISMATCH). При отказе не создаётся транзакция/receipt, ключ можно повторно использовать с корректным запросом. В CLI `database run` проверка до открытия БД, E_DATABASE_RULE. Повторная проверка при execute_on — защита общего пути. Ограничения применяются к query и к обоим видам пакетов. Не меняется формат БД, закреплён прежний NativeLog 363ccbc.

В примере продаж правила действуют на идентификаторы, цены, суммы, названия, категории и минимальную сумму фильтра. Суммы — целые единицы 0..i32::MAX. Это входные правила маршрутов, не SQL CHECK constraints и не общий механизм произвольных выражений; прямой SQL доступ не ограничен ими. Не обеспечивают валютную арифметику, ограничения суммы всех заказов или валидацию существующей БД. Повтор исторического запроса после изменения правил может быть отклонён текущей проверкой; не обещать совместимость правил между версиями.
