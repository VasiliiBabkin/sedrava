# A18 — authentication and read/write roles for SQL API

Opt-in `--auth-file ABSOLUTE_FILE` on database-api run. File is owner-owned, regular, single-link, no symlink, no group/world permissions, <=16 KiB; Unix only. JSON array of 1..32 objects {"id":"reader","sha256":"<64 lowercase hex digits>","role":"read"} or role "write" (read+write). Unique IDs and digests. Generate a cryptographically random 32-byte token (64 lowercase hex characters); store SHA-256 of the exact ASCII token, not of decoded hex. Send `Authorization: Bearer TOKEN`. No token in CLI arguments, logs or source. Missing/invalid auth -> 401; read-only principal on a write route -> 403. Write receipts scoped by auth-v1 + API name + path + stable principal ID + client key. Never reuse an ID for a different principal. Token rotation with unchanged ID preserves scope. Switching from unauthenticated A17 to A18 changes receipt namespace; do not replay uncertain old writes across that boundary without operator review. With no --auth-file, existing explicitly trusted loopback-only A17 remains available, and Authorization header is rejected. No TLS, remote access, rate limiting, row-level authorization, auth administration or production readiness. Start only on 127.0.0.1; do not publicly expose. Hash comparison scans all credentials; no formal timing-side-channel guarantee.
