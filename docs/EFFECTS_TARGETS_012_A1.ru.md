# Sedrava Effects & Targets 0.12 — A1

> Экспериментальный зависимый draft, не стабильный релиз. Этот этап
> добавляет проверяемое представление эффектов **для существующих чистых
> функций**. Он ещё не разрешает файловые операции в Core, не внедряет
> новые пользовательские эффектные функции, worker или обобщённые Result.

## Принцип

**Тип — какие значения допустимы. Эффект — какие действия допустимы.
Среда исполнения — какие полномочия фактически выданы.**

Эти три проверки не заменяют друг друга. Компилятор выводит эффекты по
типизированному графу вызовов, сравнивает их с публичными ограничениями и
разрешёнными эффектами целевой среды. В будущем runtime независимо
проверяет выданные полномочия.

## Реализовано в A1

1. Принимается необязательная аннотация чистой функции:
   \`fn title(x: int) -> int effects pure = x + 1\`.
   Старые объявления \`fn ... = ...\` сохраняются без изменений.
2. \`sedrava effects SOURCE --target app|web|android\` проверяет программу
   штатным типизированным парсером и выдаёт канонический манифест
   \`sedrava.effects.v1\` в stdout.
3. \`source_sha256\` считается по **развёрнутому источнику** после проверки
   импортов. Изменение импортированного тела меняет хеш. Это не подпись
   и не доказательство происхождения для удалённого исполнителя.
4. Отдельный модуль \`sedrava_effects.py\` анализирует транзитивный граф
   типизированных вызовов, запрещает неучтённые и косвенные вызовы,
   обнаруживает циклы, проверяет указанный верхний предел эффектов
   и отклоняет эффекты, запрещённые для \`target\`.
5. Список известных идентификаторов эффектов версионирован:
   \`host.fs.read/write/list/mkdir/rmdir\`, \`server.db.read/write\`,
   \`server.http\`, \`web.api\`. Наличие идентификатора **не**
   разрешает выполнение операции и не делает её доступной в языке.

Пример:

~~~sh
python sedrava_cli.py effects examples/effects_pure_012.sdr --target web
python sedrava_cli.py check examples/effects_pure_012.sdr
python sedrava_cli.py test examples/effects_pure_012.sdr
~~~

## Умышленно не реализовано

- \`effects { host.fs.read }\` в пользовательских \`fn\` — отклоняется;
  это будущий типизированный контракт, не поддержанный парсером эффект.
- Обязательная аннотация \`effects\` для \`export fn\`: существующие
  namespace-модули пока сохраняют старый чистый синтаксис. Переход
  будет отдельным, обратно совместимым этапом.
- Манифест A1 имеет \`kind: app-domain\`: он **не перечисляет** все
  эффекты интерфейса, браузерного хранения, серверных маршрутов и
  будущего Host. Его нельзя принимать как полный манифест безопасности
  для установки или запуска.
- Динамические функции как значения, лямбды, рекурсия и эффекты
  пользовательских функций отсутствуют в этом слое.
- Манифест не даёт разрешений ОС и не запускает программу.

## Правила будущей совместимости

- Внутри модулей эффект выводится; на границе публичного API
  будет обязательная декларация верхней границы.
- Для стабильной функции набор публично разрешённых эффектов
  допускается **сужать**, но не расширять в совместимом релизе.
- Фактические эффекты конкретной сборки выводятся независимо от
  декларации и сравниваются с политикой её целевой среды.
- Сборка и хеш манифеста должны связываться с точными проверенными
  источниками и версиями зависимостей; один \`source_sha256\`
  экспериментального A1 для этого недостаточен.
- Для ветви с Host понадобится общий Core 0.12, включающий
  типизированные варианты ошибок, \`match\` и \`Result\`.
  Host A1/A2 не объединяются с Core этим PR.

Дальше: эффекты импортированных публичных функций и проверка на уровне
основного компилятора для всех target, открытые/закрытые типы ошибок
с полями, проверяемый \`match\`, затем интеграция Host A3. Только
после независимого CI, аудита безопасности и пересмотра владельцем.
