# Сервисный журнал A31 · 0.1.0

Экспериментальное локальное приложение для учёта обслуживания оборудования: ОПС, СКУД, видеонаблюдение, связь и другие системы. Создано на опубликованных Sedrava 0.12.0-alpha.3 и NativeLog 0.0.2. Прикладные исходники — app.sdr, api.sdr, migrations.json, sedrava-project.json. JavaScript, HTML и CSS генерирует Sedrava; отдельный прикладной backend не используется. Python и Node — только тестовые инструменты разработчика.

## Установка и запуск

Linux x86-64 GNU (Ubuntu 24.04 проверена). Установите [платформу A30](https://sedrava.virtreal.ru/downloads/0.12.0-alpha.3/) по инструкции, добавьте её bin в PATH. Войдите в каталог проекта (service-desk внутри готового ZIP или examples/service_desk в репозитории).

```sh
sedrava --version
sedravasql-native-preview --version
sedrava test
sedrava build
```

Если вы используете готовый пакет, вместо build можно выполнить sedrava project verify-package . из его каталога. Для первого запуска создайте новый приватный каталог данных (не используйте прежнюю базу). Следующие команды выполнить **один раз** в своей доверенной локальной консоли. Они требуют openssl и sha256sum для подготовки случайного ключа, но самому приложению эти утилиты не нужны. Не вставляйте ключ в публичные чаты или исходники.

```sh
umask 077
DATA="$HOME/service-desk-data"
mkdir -m 700 "$DATA" || exit 1
KEY=$(openssl rand -hex 32) || exit 1
HASH=$(printf '%s' "$KEY" | sha256sum | cut -d ' ' -f 1)
printf '[{"id":"operator","sha256":"%s","role":"write"}]\n' "$HASH" > "$DATA/auth.json"
printf '%s\n' "$KEY" > "$DATA/operator-key.txt"
unset KEY HASH
sedrava migrate --data "$DATA" --trusted --apply
```

При каждом запуске из каталога проекта:

```sh
DATA="$HOME/service-desk-data"
sedrava serve --data "$DATA" --auth-file "$DATA/auth.json" --trusted --allow-write --port 8080 --idle-ms 120000
```

Если порт занят, выберите другой. Откройте http://127.0.0.1:8080/ в браузере на той же машине. Войдите ключом из приватного operator-key.txt. Сессия по умолчанию 900 секунд, сервер имеет ограничение числа запросов (1000) и времени простоя. Завершайте сервер штатно; не удаляйте lock-файлы работающего процесса. Не выставляйте сервис через публичный reverse proxy. Для чтения без права изменения можно отдельно создать пользователя с ролью read по SERVER_SESSIONS_A23D.ru.md из дистрибутива.

## Рабочий пример

1. Заказчики и объекты: заказчик c01, условный контакт; объект s01 для c01.
2. Оборудование: a01 для s01, например контроллер СКУД, условный серийный номер.
3. Создать заявку t01 для a01, указать описание, приоритет 1–3 и дату. Создаётся также событие t01.
4. Сводка: загрузить открытые заявки. Скопировать текущее значение last_event (сначала t01).
5. Работа и статус: событие w01, заявка t01, ожидаемая версия t01, дата, описание, 45 минут, 1500 рублей. Записать работу.
6. Обновить список: last_event теперь w01. Закрыть заявку новым событием w02 с ожидаемой версией w01 и причиной. При необходимости повторно открыть новым событием.
7. История и итоги: указать t01, загрузить историю и подсчитать минуты/стоимость. Каждое изменение требует нового ID события; ID нельзя использовать повторно. Списки до 20 строк, для следующей страницы ввести последний ID.

## Инварианты

Пять связанных таблиц: Clients → Sites → Assets → Tickets → Events. 14 миграций: пять таблиц, пять индексов, четыре внешних ключа. 15 маршрутов, 15 типизированных UI-сервисов, шесть разделов. Создание заявки и исходного события атомарны. Запись работ, закрытие и повторное открытие обновляют заявку и добавляют событие одной транзакцией. Сравнение last_event защищает от устаревшей записи; уникальный ID события исключает повторное использование версии. Дубли и несуществующие родительские записи отклоняются. Неуспешные транзакции не оставляют частичных данных. Повтор с тем же ключом и параметрами возвращает прежнюю квитанцию. При потере ответа повторите прежние поля в той же сессии/под тем же пользователем; выход или перезагрузка страницы теряет локальный ключ повтора.

## Проверка и ограничения

A31 пройден на бинарниках A30: 68 прямых HTTP-запросов и 24 HTTP-запроса из сгенерированного DOM (jsdom), включая одновременные записи двух пользователей, rollback, restart, неизменность пакета, повтор потерянного ответа, XSS-safe text, авторизацию, шесть разделов, отчёт 105 минут / 4000 RUB. Настоящий браузер и мобильная визуальная приёмка не проводились. Исходный язык и СУБД не менялись.

Это проверяемый функциональный прототип, не готовая промышленная система. Ручные ID и курсоры, нет выбора строк из удалённых таблиц, автоматического обновления, глобального поиска, редактирования справочников, назначения исполнителей, SLA, вложений, автоматических серверных временных меток или аудита личности автора внутри события. Дата вводится вручную и проверяется только по длине 10 символов, а история сортируется по ID, не по времени. Стоимость — целые рубли, не бухгалтерский учёт. NativeLog ограничен размером журнала, количеством транзакций и бюджетом сканирования; один писатель/один процесс сервера, не публичный многопользовательский продукт. Не храните реальные персональные данные или ценные рабочие записи в экспериментальном выпуске. Не обещается восстановление при физическом отказе или потере питания. Следующий приоритет — нативный выбор удалённых записей и удобное обновление UI, валидация дат, история с серверным временем/автором, проверка резервного восстановления и реального браузера.
